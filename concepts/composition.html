Composition

A form produces a QuestionnaireResponse — a list of answers. To turn those answers into a structured clinical document, you send them to the SDC server's $extract operation together with a Composition template. The server evaluates the FHIRPath embedded in each section and returns a finished Composition resource. The two examples below — a short radiology note and a multi-section pathology report — use the exact same $extract call; only the template differs.

Example 1 — A radiology note

Two sections. Each uses a templateExtractContext FHIRPath expression to pick the relevant answer, and a text.div with a {{%context.answer.valueString}} placeholder. After extraction the placeholders hold real values, returned inside a transaction Bundle.

          slot="questionnaire">
  {
    "resourceType": "Questionnaire",
    "url": "http://example.org/Questionnaire/radiology-note",
    "version": "1.0.0",
    "status": "active",
    "item": [{
      "linkId": "report",
      "type": "group",
      "text": "Radiology Report",
      "item": [
        { "linkId": "findings",   "type": "text", "text": "Findings" },
        { "linkId": "impression", "type": "text", "text": "Impression" }
      ]
    }]
  }
  </script>
</tiro-form-filler>

                    

                

            


            
            
Example 2 — A multi-section pathology report

            

                The same call scales to a full document. This template has five sections — Specimen, Clinical History,
                Gross Description, Microscopic Description and Diagnosis — each pulling a different answer by
                linkId. Each section also carries its standard LOINC section code (shown next to
                the title), and the Diagnosis section wraps its value in <strong> to make the headline
                finding stand out. Edit any field and re-run to watch the report regenerate.

<!-- Same SDK element, a five-field Questionnaire -->
<tiro-form-filler id="pathology-form">
  <script type="application/fhir+json"
          slot="questionnaire">
  {
    "resourceType": "Questionnaire",
    "url": "http://example.org/Questionnaire/pathology-report",
    "version": "1.0.0",
    "status": "active",
    "item": [{
      "linkId": "report",
      "type": "group",
      "text": "Surgical Pathology Report",
      "item": [
        { "linkId": "specimen",         "type": "text", "text": "Specimen" },
        { "linkId": "clinical-history", "type": "text", "text": "Clinical history" },
        { "linkId": "gross",            "type": "text", "text": "Gross description" },
        { "linkId": "microscopic",      "type": "text", "text": "Microscopic description" },
        { "linkId": "diagnosis",        "type": "text", "text": "Diagnosis" }
      ]
    }]
  }
  </script>
</tiro-form-filler>

                    

                

            


            

                How it works. Template-based extraction never touches the questionnaire's content — it
                runs entirely off the answers. Each section's templateExtractContext FHIRPath
                (repeat(item).where(linkId='…')) picks a slice of the QuestionnaireResponse, exposed to
                the template as %context. Sections whose context resolves to nothing are dropped, and the
                templateExtractContext extension is stripped from the output — while each section's
                code (a LOINC document-section code, e.g. 22637-3 for the final diagnosis) is
                carried straight through, so downstream systems can identify sections regardless of title or language. The
                questionnaire
                parameter is required (a minimal stub with an id is enough) — without it the server tries
                to resolve the response's canonical URL and fails.
